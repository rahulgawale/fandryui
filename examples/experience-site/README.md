# Experience site example: Aryabh Outfitters

The fandry product blocks on a real Salesforce Commerce store (LWR), with products, prices and a cart from the store's own Storefront APIs, and no Apex. It is laid out like `examples/salesforce`: your code in `force-app`, Fandry's in `fandryui` (generated by `fandry add`, gitignored here).

```
force-app/main/default/
  lwc/aryabhStoreData/          # data layer: the only module that fetches (commerce/* Storefront APIs)
  lwc/aryabhCatalog/            # UI: fandry-product-catalog on the category page
  lwc/aryabhFeaturedProducts/   # UI: a row of product cards on Home
  lwc/aryabhProductDetail/      # UI: the product page (loads through the data layer, adds to the cart)
  lwc/aryabhProductDetailView/  # UI: the product page's markup, FdProductCardState with its own template
  lwc/aryabhProductCard/        # fandry-product-card that hides a missing price
  objects/                      # Color on ProductAttribute; swatch colour and flair on Product2
  productAttributeSets/Color    # variations differ by Color
  permissionsets/Aryabh_Storefront         # read access to the custom fields, for shoppers
  digitalExperiences/site/Aryabh_Outfitters1/   # the Home, category and product pages, which use the components
data/products.json              # the store's products: prices, colours, images
scripts/setup-store.mjs         # builds the store's data from products.json
fandryui/main/default/lwc/      # fandry bundles, from `fandry add`
```

## UI and data

The UI components (`aryabhCatalog`, `aryabhFeaturedProducts`) show what they're given and say what happened; they fetch nothing and know no Commerce type. `c/aryabhStoreData` is the data layer and the only module that fetches. It uses the store's Storefront APIs, the same modules the store's built-in components use, so the shopper's entitlements, price books, strikethrough prices and cart apply as everywhere else in the store:

- `commerce/productApi`: `searchProducts` (one ungrouped search returns every sellable variation with its image, colour and swatch), `getProduct` (once per product: a variation's parent and colour order), `getProductCollection` (the parents' fields, in one call) and `getProductPricingCollection` (every price, in one call)
- `commerce/cartApi`: `addItemToCart`, which also updates the store's cart badge
- `commerce/contextApi`: `getSessionContext`, to know whether a shopper is logged in

It returns products in the shape fandry-product-card and fandry-product-catalog take, and turns a chosen swatch back into its variation for the cart.

The product page is split the same way: `aryabhProductDetail` loads the product (`loadProduct`: every colour with both pictures, and the prices) and adds to the cart (`addToCart`, with a quantity), and `aryabhProductDetailView` is only markup. The view extends fandry's `FdProductCardState` with a page template of its own -- gallery, colours, quantity, Add to cart -- so swatch selection, prices, flairs and the discounted-price phrase come from the block, not a copy of it.

The catalog renders `c/aryabhProductCard` through `card-component`: the block's extension point, used here for the one store-specific change (no price shows blank rather than $0.00) instead of copying the card.

## Set it up

```bash
# from the repository root
npm run build:npm
npm run example:experience        # fandry init + fandry add product-catalog toast toastViewport spinner

cd examples/experience-site
sf project deploy start --source-dir force-app/main/default/objects --target-org <org>
sf project deploy start --source-dir force-app/main/default/permissionsets --target-org <org>
sf org assign permset --name Aryabh_Storefront --target-org <org>
sf project deploy start --source-dir force-app/main/default/productAttributeSets --target-org <org>
sf project deploy start --source-dir fandryui --source-dir force-app --target-org <org>
node scripts/setup-store.mjs --target-org <org>
sf community publish --name "Aryabh Outfitters" --target-org <org>
```

The fields go first: the attribute set and the permission set name them. Only the three pages that use the components are kept here; the rest of the site is the store template's, and a deploy leaves it as it is. The Home page's Featured component takes a category ID (the catalog's top category); set it in Experience Builder for another org.

`setup-store.mjs` can be run again: it adds what's missing and never deletes.

To try the store while it's private, log in as a shopper: a contact under a buyer account in the store's buyer group, with the site's shopper profile and the standard Buyer and Aryabh Storefront permission sets. Salesforce requires the account's owner to have a role.

## Status

Verified on the org `fandry-demo-site`, logged in as the test shopper: Home shows the featured cards; the product page shows the product's pictures, flairs, colours (choosing one swaps the pictures), quantity and Add to cart, which calls the store's cart with the chosen colour's variation and quantity; the category page lists the 9 products with their colours, images, flairs and category filter (and the store's Shop by Category tiles); the colour filter switches each card to the matching variation; the cards link to the store's product pages.

**Prices and the cart aren't working yet, in the store itself.** Its pricing service answers "The buyer account is not a member of the store" for the test shopper, and the cart rejects items with INVALID_INPUT_COMBINATION ("account ... does not belong to webstore"); the store's own product page shows no price and a disabled Add To Cart too. The account is an active buyer in the store's buyer group, and that group has the store's price book. Until that's resolved, the components show products without prices and say why, and add to cart names the store's error in a toast.
